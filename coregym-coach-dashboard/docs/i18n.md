# Dashboard i18n (EN / AR)

Bilingual dashboard: English + Egyptian-Arabic with full RTL support.
Language is stored in the `coregym-lang` cookie and read SERVER-side, so both
server and client components render the active language with no flash.

## Architecture (`src/lib/i18n/`)

| File | Role |
| --- | --- |
| `config.ts` | `Lang` type, cookie name, `intlLocale()` |
| `dictionary.ts` | Merges domain dicts, exports `tFor(lang)` and the strict `TKey` type |
| `translate.ts` | Dot-path lookup, `{var}` interpolation, English fallback |
| `format.ts` | Locale-aware date/number/currency formatters |
| `server.ts` | `getI18n()` for RSC — reads the cookie |
| `client.tsx` | `I18nProvider` + `useI18n()` for client components |
| `domains/*.ts` | One file per feature area, each `{ en: {...}, ar: {...} }` |

## Usage

Server components (pages, layouts):

```tsx
const { t, fmt, lang, dir } = await getI18n();
t("overview.kpi.activeClients")
fmt.date(someDate)
```

Client components (`"use client"`):

```tsx
const { t, fmt, lang, setLang } = useI18n();
t("workouts.empty.title")
t("common.time.minsAgo", { n: 5 })   // interpolation
```

Keys are compile-time checked against the English dictionary (`TKey`), so a
typo or a missing key fails `tsc`. `t()` falls back to English at runtime if
an Arabic key is missing, but every key must still exist in BOTH languages —
`tests/i18n-parity.test.ts` verifies en/ar key parity.

## Adding strings

Add keys to the domain file for your feature (`src/lib/i18n/domains/<area>.ts`),
in BOTH the `en` and `ar` blocks with identical key paths. Reuse `common.*`
(actions, empty states, table headers, relative time, confirm dialogs) instead
of duplicating.

### Register & style (Arabic)

- Egyptian colloquial, same tone as the landing page (`src/components/landing/i18n.ts`).
  Match the landing's habits: coach → "كوتش", client → "عميل", dashboard → "داشبورد",
  sets/reps/streaks often stay English.
- Keep brand names and technical nouns as-is: CoreGym, Stripe, iOS, AI, kg, kcal.
- Numbers stay Latin (0-9) — formatters already handle this.
- Legal pages (privacy/terms) use Modern Standard Arabic instead.
- Encourage, don't command: "سجّل تمرينك" not "يجب عليك تسجيل تمرينك".

## Formatting rules

Never hardcode `toLocaleDateString("en-US")` / `$` / `toFixed` — use `fmt`:

| Need | Call |
| --- | --- |
| Short date | `fmt.date(d)` → "Sep 29, 2026" / "29 سبتمبر 2026" |
| Date + time | `fmt.dateTime(d)` |
| Grouped number | `fmt.num(1234567)` → "1,234,567" |
| USD from cents | `fmt.money(cents)` → "$1,234.56" |
| USD from dollars | `fmt.moneyShort(dollars)` |
| Percent | `fmt.percent(87.5)` |

## RTL rules

`<html dir>` flips automatically. Your job is removing physical-direction CSS:

- `ml-*`/`mr-*` → `ms-*`/`me-*` — margins
- `pl-*`/`pr-*` → `ps-*`/`pe-*` — padding
- `left-*`/`right-*` (positioning) → `start-*`/`end-*`
- `-left-*`/`-right-*` → `-start-*`/`-end-*`
- `text-left`/`text-right` (layout) → `text-start`/`text-end`
- EXCEPTIONS: `text-left`/`text-right` on numeric/data table cells and
  chart labels stay physical (numbers align consistently in both directions);
  `left-1/2 -translate-x-1/2` centering stays as-is.
- recharts SVGs are not RTL-aware: wrap the chart container in
  `<div dir="ltr">` and let axis/tooltip text use `fmt` — Arabic labels inside
  an LTR chart render fine.
- Absolute-positioned badges/counters: `right-0` → `end-0`, etc.

## Don't translate

- API/server error messages surfaced via `err.message` (English technical copy
  is fine); only localize strings hardcoded in the component itself.
- Database content (exercise names, food names, client names).
- Brand/product names.
